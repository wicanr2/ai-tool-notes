# PEFT 與 LoRA adapter：為什麼十幾 MB 能改變一個 15 GB 的模型

一份實際交付的 LoRA adapter 只有 18.2 MB、428 萬個參數，卻能把一個 78 億參數的模型在特定任務上的正確率從 25% 拉到 87.5%。這個比例（adapter 是 base model 的 0.05%）看起來不合理，但它其實是微調這件事的常態——而不是例外。

這篇拆解三個問題：全參數微調的成本到底花在哪、PEFT 這一族方法各自繞開了哪一項、LoRA 為什麼在其中勝出成為事實標準。

- 相關：[在 gemma-4-E4B-it 上掛載 LoRA adapter](gemma4-lora-adapter-guide.md)（實際檔案與載入步驟）、[vLLM 架構與 KV cache](vllm-serving-and-architecture.md)

## 一、全參數微調的帳單

要理解 PEFT 存在的理由，得先看清楚它想省掉什麼。訓練一個模型時，顯存被四樣東西吃掉：

| 項目 | 大小（以 P 個參數、bf16 訓練為例） | 說明 |
|---|---|---|
| 模型權重 | 2P bytes | 前向與反向都要 |
| 梯度 | 2P bytes | 每個參數一份 |
| 優化器狀態 | 8P～12P bytes | Adam 要存一階動量、二階動量，通常還要一份 fp32 主權重 |
| 啟動值（activation） | 隨 batch 與序列長度變動 | 反向傳播要用 |

前三項加起來大約是 **12P～16P bytes**。一個 78 億參數的模型，光是「權重 + 梯度 + 優化器狀態」就要 94～125 GB——單張 80 GB 的卡放不下，得靠多卡切分或 offload。

關鍵在於：**這筆錢有八成付給了梯度與優化器狀態，而不是模型本身。** 如果能讓絕大多數參數不需要梯度，這三項裡的後兩項就幾乎歸零，只剩下 2P 的權重需要放在卡上（而且可以量化）。

PEFT（Parameter-Efficient Fine-Tuning，參數高效微調）就是這個想法的統稱：**凍結預訓練權重，只訓練一小組參數。**

值得先釐清一件事：省的主要是**訓練成本**，不是推論成本。推論時模型還是那麼大，該讀的權重一個都不會少。PEFT 換來的推論好處是另一回事——一份 base model 可以同時服務很多個 adapter（見第六節）。

## 二、PEFT 這一族方法

「只訓練一小組參數」有很多種做法，差別在於那組參數放在哪裡。

| 方法 | 做法 | 推論延遲 | 能否合併回權重 |
|---|---|---|---|
| **Adapter layers** | 在每層之間插入小型瓶頸模組 | 增加（多了序列化的層） | 否 |
| **Prefix tuning** | 在每層的 K/V 前面接上可訓練的虛擬 token | 增加（吃掉 context 長度） | 否 |
| **Prompt tuning** | 只在輸入端接可訓練的虛擬 token | 略增 | 否 |
| **BitFit** | 只訓練 bias 項 | 不變 | 是（本來就是原參數） |
| **IA³** | 學一組縮放向量，逐元素乘上 K、V、FFN 的啟動值 | 幾乎不變 | 是 |
| **LoRA** | 對權重矩陣學一個低秩增量 | 不變或略增（可選擇合併） | **是** |

LoRA 成為主流的原因就在最後一欄與倒數第二欄：**它是唯一同時做到「表達力足夠」與「推論時可以完全零額外開銷」的做法。**

Adapter layers 在每層插入新模組，等於加深了網路，每個 token 都要多走幾層；prefix tuning 佔用 context 預算，而那正是長對話最稀缺的資源。LoRA 學的是「原本那個矩陣要改多少」，所以可以直接把改動加回原矩陣，之後的模型是一個結構完全沒變的普通模型。

另外要注意 **PEFT 這個詞有兩個意思**：一個是上面說的方法統稱，另一個是 Hugging Face 的同名套件。後者順帶定義了 adapter 的事實標準檔案格式——vLLM、TGI、SGLang 都認得它，交付時說「PEFT 格式 LoRA adapter」講的是這件事。

## 三、LoRA 的數學

### 低秩假設

微調要做的事，形式上是給每個權重矩陣 `W` 找一個增量 `ΔW`，讓 `W + ΔW` 在新任務上表現更好。全參數微調直接把 `ΔW` 當成一個和 `W` 同樣大的自由矩陣去學。

LoRA 的出發點是一個觀察：**微調帶來的 `ΔW` 通常是低秩的。** 一個 `d × k` 的矩陣理論上有 `d × k` 個自由度，但「讓模型在什麼情境下呼叫哪個工具」這種調整，實際需要的自由度遠低於此——它改的是行為的少數幾個方向，不是把整個表示空間重新洗牌。

既然如此，就把 `ΔW` 強制寫成兩個瘦矩陣的乘積：

```
ΔW = B · A       其中 A 是 r × k、B 是 d × r，且 r ≪ min(d, k)
```

前向傳播變成：

```
h = W·x + (α / r) · B · A · x
     ↑凍結        ↑只有這兩個要訓練
```

### 參數量

以實際交付的那份 adapter 為例，`r = 8`，掛在 `gemma-4-E4B-it` 的注意力投影上：

| 模組 | 原矩陣形狀 | 原參數量 | LoRA 參數量（A + B） |
|---|---|---|---|
| `q_proj` | 2048 × 2560 | 5,242,880 | 8×2560 + 2048×8 = 36,864 |
| `k_proj` | 512 × 2560 | 1,310,720 | 8×2560 + 512×8 = 24,576 |
| `v_proj` | 512 × 2560 | 1,310,720 | 24,576 |
| `o_proj` | 2560 × 2048 | 5,242,880 | 8×2048 + 2560×8 = 36,864 |

單看 `q_proj`：524 萬降到 3.7 萬，少了 **99.3%**。整份 adapter 132 個模組加總 4,276,224 個參數，FP32 儲存 18.2 MB。

### 初始化：為什麼訓練起點等於原模型

`A` 用高斯隨機初始化，`B` 初始化為**全零**。於是訓練開始的那一刻：

```
ΔW = B · A = 0 · A = 0
```

模型的行為與 base model 完全相同。這個設計很重要——它讓微調變成一個從「原模型」出發的平滑過程，不會在第一步就把預訓練學到的東西打亂。反過來若兩邊都隨機初始化，訓練起點就是一個被隨機擾動過的模型，收斂會困難得多。

### 為什麼低秩就夠

支持這個假設的實證是「內在維度」（intrinsic dimensionality）這一系列研究：把預訓練模型的微調限制在一個隨機的低維子空間裡，往往只需要幾百到幾千個維度就能達到接近全參數微調的效果。預訓練已經把通用能力學好了，下游任務要做的是在既有表示上挑選與重新加權，不是重建表示本身。

這也劃出了 LoRA 的適用邊界：**調整行為、風格、格式、任務對齊，低秩夠用；要灌入模型完全沒見過的大量知識，低秩就不夠。** 後者該考慮的是繼續預訓練或 RAG，不是把 `r` 從 8 調到 512。

## 四、超參數怎麼選

### rank（`r`）

`A` 與 `B` 之間那條「腰」的寬度，決定 adapter 的容量。

| 任務型態 | 常見 `r` |
|---|---|
| 格式對齊、工具呼叫決策、語氣風格 | 8 – 16 |
| 較複雜的領域行為、多任務 | 32 – 64 |
| 大量新知識注入 | 128+（但通常代表選錯方法了） |

`r` 一旦訓練完成就固化在權重形狀裡，載入時不能改。要換只能重訓。

實務上 `r` 過大的症狀不是「更好」而是**過擬合**：訓練 loss 漂亮，評測分數卻在某個 step 之後往下掉。這也是為什麼挑 checkpoint 是微調流程的一部分——訓練越久不等於越好。

### alpha 與縮放係數

`lora_alpha` 搭配 `r` 決定 adapter 的強度，實際縮放係數是 `α / r`。`α = 16`、`r = 8` 時係數為 2.0。

拆成兩個參數的理由是**解耦**：調整 `r`（容量）時不希望整體強度跟著跑掉，所以用 `α` 補回來。常見慣例是 `α = 2r` 或 `α = r`。

這是唯一一個在部署階段還能有意義調整的旋鈕：改 `adapter_config.json` 裡的 `lora_alpha` 就等於整體縮放 adapter 的影響力。調低讓行為靠回 base model，調高則加強。但每動一次都要重跑評測——交付的分數是在特定 `α` 下量到的，換一個值那個數字就不再成立。

### 掛在哪些模組上

| 選擇 | 效果 |
|---|---|
| 只掛 attention 的 `q` / `v` | 原始 LoRA 論文的配置，最省 |
| attention 全部（`q`/`k`/`v`/`o`） | 常見預設，改變「模型怎麼在情境間做選擇」 |
| 加上 MLP（`gate`/`up`/`down`） | 參數量大增，改變「模型記得什麼」 |
| 加上 `embed_tokens` / `lm_head` | 只有在擴充詞彙表時才需要，且會讓 adapter 大很多 |

經驗法則：**要改行為就掛 attention，要改知識才動 MLP。** 工具呼叫決策屬於前者。

有一個架構層面的例外值得注意：某些模型的後段層會共享前面層的 KV cache（`gemma-4-E4B-it` 的最後 18 層就是如此），這些層的 `k_proj` / `v_proj` 輸出根本不進注意力計算，掛 LoRA 上去不會改變任何輸出。挑 target 之前要先確認模型架構，不能一律套用「所有層都掛」（機制見 [vLLM 架構與 KV cache](vllm-serving-and-architecture.md)）。

### 學習率

LoRA 的學習率通常比全參數微調**高一個數量級**（`2e-4` 對上 `2e-5` 這種量級）。原因是要訓練的參數少得多、而且 `B` 從零開始，需要較大的步伐才能在有限的 step 內動起來。

### dropout

`lora_dropout` 只在訓練期作用，推論時完全不生效。載入既有 adapter 時這一欄可以無視。

## 五、一份 adapter 裡有什麼

最小可用集合只有兩個檔案：

```
my-lora/
├── adapter_config.json          怎麼掛：r、alpha、target_modules、base model
└── adapter_model.safetensors    掛什麼：每個目標模組的 lora_A 與 lora_B
```

張量的命名規則決定它能不能對上 base model：

```
base_model.model.<模組在 base model 裡的完整路徑>.lora_A.weight
```

PEFT 在 base model 外面包一層 `base_model.model.`，後面接的是原始路徑。**載入時 base model 的模組路徑必須逐字對上**，對不上的後果通常不是報錯，而是靜默掛上 0 個模組——模型照常回答，只是回答的是完全沒調過的版本。

逐欄位的說明、形狀規則、以及一段不必載入模型就能檢查相容性的程式碼，見 [LoRA adapter 教學](gemma4-lora-adapter-guide.md)。

**adapter 裡沒有 tokenizer，也沒有 chat template。** 這兩樣來自 base model 的 repo，而它們的版本一致性跟權重一樣重要：LoRA 學到的是「在訓練時那種文字排列之後接什麼」，換一份 chat template，模型看到的就是沒學過的前綴。實測過同一份 adapter 只換樣板，就從「正確拒答」變成「呼叫一個工具清單裡不存在的函式」。交付 adapter 時應該連同訓練用的樣板檔案或其 commit hash 一起給。

## 六、部署形態

### 合併 vs 動態掛載

**合併（merge）**把 `(α/r)·B·A` 直接加進 `W`，輸出一份新的完整權重：

```python
merged = PeftModel.from_pretrained(base, ADAPTER).merge_and_unload()
```

推論時零額外開銷，部署對象是一個普通模型。代價是產生一份與 base 同樣大的新檔案、失去切換能力，而且是單向的——合併後無法還原成 adapter，所以原始 adapter 目錄一定要留著。

**動態掛載**保持兩者分離，推論時即時計算 `W·x + (α/r)·B·A·x`。多了一次小矩陣運算，但換來三件事：可隨時開關、可切換不同 adapter、以及下面這個。

### 一個 base model 服務多個 adapter

這是 LoRA 在推論端真正的經濟性所在。15 GB 的 base 權重只需要載入一次，每個 adapter 只多佔十幾 MB：

```bash
vllm serve <base-model> \
  --enable-lora \
  --lora-modules 客戶A=/path/a 客戶B=/path/b 客戶C=/path/c \
  --max-lora-rank 16 --max-loras 4
```

服務會同時提供 base 與每個 adapter 各自的 model id，請求靠 `model` 欄位選擇。vLLM 用專門的批次核心（batched LoRA kernel）讓同一批請求裡不同序列套用不同 adapter，不需要為每個 adapter 各開一個服務。

三個 adapter 各開一個完整服務要 45 GB；共用 base 則是 15 GB + 54 MB。這個差距讓「每個客戶一份微調」在成本上變得可行。

實務上兩個容易踩到的點：`--max-lora-rank` 必須 ≥ 所有 adapter 中最大的 `r`（設小了直接拒載）；請求的 `model` 欄位填成 base model 名稱會走沒調過的模型，**而且不會有任何警告**。

## 七、幾個值得知道的變體

| 變體 | 改了什麼 | 什麼時候用 |
|---|---|---|
| **QLoRA** | base model 以 4-bit 量化載入，LoRA 仍用高精度訓練 | 訓練端顯存不足時。注意量化的是訓練時的 base，產出的 adapter 仍要套回對應的模型 |
| **rsLoRA** | 縮放係數從 `α/r` 改成 `α/√r` | 用較大的 `r`（32 以上）時，避免有效學習率被 `r` 壓下去 |
| **DoRA** | 把權重拆成「大小」與「方向」兩部分，只對方向做低秩調整 | 小 `r` 下想更接近全參數微調的效果，代價是推論多一點開銷 |
| **LoRA+** | 給 `A` 和 `B` 不同的學習率 | 收斂偏慢時的低成本改善 |

`adapter_config.json` 裡的 `use_rslora` 與 `use_dora` 兩個布林欄位就是在標記這些變體。載入時它們會改變縮放的算法，所以**不能自行改動**——那是訓練時的設定，不是部署選項。

## 八、常見誤解

**「adapter 可以套在任何同名模型上。」** 不行。張量名稱與形狀必須逐一對得上 base model 的實際權重，連量化版本都不行——LoRA 的 `A`、`B` 是相對於特定精度的權重分佈訓練出來的，套到 FP8 或 AWQ 量化版上就算維度湊得起來，行為也不保證。

**「`adapter_config.json` 裡寫了 base model，所以載入時會自動檢查。」** 那一欄只是紀錄。PEFT 不會去下載它，也不會驗證你正在載入的模型是不是它——掛錯 base 不會有人提醒。

**「`r` 越大效果越好。」** 過了任務需要的容量之後，增加 `r` 帶來的是過擬合與更慢的收斂，不是更好的分數。

**「多個 adapter 可以直接疊加。」** 數學上可以（PEFT 提供 `add_weighted_adapter`），但兩個各自訓練的 adapter 相加沒有理論保證，結果通常需要重新評測才知道能不能用。

**「離線評測分數高就可以上線。」** 評測集的組成決定了你量得到什麼。若評測題目全是「該呼叫工具」的情境，模型學成「走到這個位置就是要發 tool call」這種退化根本量不到——評測集裡必須有一批「不該呼叫任何工具」的題目。這一類漏洞在上線前是隱形的。
