# DeepSeek-V4 × J-Space 報告評讀，以及單卡 L40S 能不能自架

一份 2026 年 8 月發布的報告主張：DeepSeek-V4 的 Agent 表現波動主要不是模型能力不足，而是「能力實現損失」——能力要穿過推理模式、首輪介面、工具 schema、長程狀態與驗證機制才能變成可交付結果，任何一層失配都會折損。報告用 J-Space Cognition Suite 這個外掛做開關實驗，並附上九項 benchmark 的對照數字。

這篇做兩件事：評讀那份報告的主張與證據強度，以及回答一個具體的工程問題——手上那台單卡 L40S 的機器能不能把 DeepSeek-V4 架起來。

**評讀與量測日期：2026-08-18。**

## 報告的核心主張

### 能力實現損失

報告的核心概念是把「模型有沒有這個能力」與「這個能力有沒有變成結果」分開。它主張 DeepSeek-V4 兩個型號的基礎能力都已經很強（Pro 1.6T 總參數 / 49B 激活，Flash 284B 總參數 / 13B 激活，皆支援 1M context），複雜任務失敗多半發生在能力到結果之間的傳導層，而不是能力本身不足。

具體列出的損失點包括：目標在機械執行階段淡出、同一個名稱或約束在不同分支被各自重建、工具失敗後空白重試而沒有繼承診斷、舊計畫仍佔著 context 卻已不是行動依據、以及模型高估完成度而沒有核對驗證覆蓋。

這一段的框架本身是站得住的工程觀察，跟長 Agent 任務的實務經驗吻合。「長 context 不等於有效工作記憶」這句尤其準確。

### Minimal 介面過擬合

報告引用第三方 repo [dsh-anchored-standard](https://github.com/xiaobright/dsh-anchored-standard) 的變數分離實驗，主張 DeepSeek-V4 的 Agent 後訓練與具體的介面指紋綁在一起：官方 Minimal 的兩工具 schema 會穩定錨定某一種推理軌跡，換成其他工具 schema 則進入另一種；加入 AGENTS/CLAUDE 摘要或 Skill 目錄提醒會破壞錨定。

換句話說，後訓練學到的行為沒有完全抽象成與介面無關的通用策略。這個現象若成立，對任何要串接 DeepSeek 的系統都是重要的——**你的工具宣告怎麼寫，會改變模型的推理軌跡，而不只是改變它知道有哪些工具**。

這與本 repo 先前在 gemma-4 上實測到的現象是同一類問題：同一個 LoRA adapter，只換 chat template 就從「正確拒答」變成「呼叫工具清單裡不存在的函式」（見 [LoRA adapter 教學](gemma4-lora-adapter-guide.md)）。序列化格式不是包裝，它是模型輸入的一部分。

### 思維鏈二極體

報告把「persona 或工具面的小變化引發離散的行為躍遷，而非成比例變化」這個現象命名為 chain-of-thought diode，並明確聲明這是對黑箱行為的工程概括，不是 DeepSeek 官方的架構名稱。附帶的觀察包括：中間混合區比兩端都不穩定、第一輪形成路徑承諾後尾部追加 persona 難以改變軌跡、極短路徑會跳過驗證而極長路徑遲遲不行動。

### J-Space 做了什麼

不改模型權重，是推理時的控制層。三級門控依任務複雜度決定要載入多少機制（`fast` 單步不加機制、`full` 有限多步載一到兩個模組、`loop` 多檔多工具啟用帳本與 checkpoint），並用一份只保留 `Goal / Core / Verified / Open / Next` 五類狀態的帳本，讓模型在工具呼叫、檔案切換與 context 壓縮之後還能恢復同一個任務狀態。

另一個設計是把「監控」變成「控制」：每個檢查訊號都必須改變行動——可信則繼續、可診斷的失敗要帶著診斷重試、發現退化則回到最近的已驗證狀態。checkpoint 同時記錄驗證器與覆蓋範圍，避免把局部測試通過誤報成整體完成。

## 證據強度評估

報告附了九項 benchmark 的對照表，其中 V4-Pro + J-Space 在七項位居對照列首位。這些數字要怎麼讀，報告自己在第 6 節講得比多數同類文件都誠實，以下是本文的評估。

**單次執行，沒有信賴區間。** 報告明白寫著「所有結果按單次執行記錄，不表示多次均值，也不附帶信賴區間」。這意味著表格裡 82.7 對 87.1 這種差距，無法與執行間的自然變異區分開來。溫度設在 1.0（非貪婪），單次取樣的浮動只會更大。要支持因果宣稱，需要多隨機種子與逐任務軌跡日誌——報告自己也是這樣說的。

**跨廠商欄位不是同一 harness。** GLM-5.3、Kimi-K3、Opus-4.8、Fable 5 的數字沿用各廠商公開時的評測方法。所以「超越 Fable 5」描述的是公開能力位置，不是受控比較。真正受控的只有「同模型、同 harness、開關 J-Space」這一組對照，而那組才是報告的因果宣稱所在。

**效率表用了未公開的統一縮放係數。** 得分/時間 0.43 → 1.09、得分/Token 0.38 → 0.84，報告註明「採用固定統一係數縮放」。絕對值因此不具意義，只有 2.53× 與 2.21× 這兩個比值可讀。這種寫法會讓讀者誤以為那是原始量測值，是這份報告在呈現上最弱的一處。

**作者與受測對象是同一人。** 報告作者即 J-Space 的作者。這不使結果無效，但它不是獨立評測，解讀時要按內部測試看待。

**主動列出可證偽條件是真正的加分。** 報告第 6 節列了六個「若出現則直接推翻本文強主張」的結果，例如「得分上升僅來自更大 Token 或更長時間，而得分/時間與得分/Token 同時下降」、「`we` 詞頻上升但行動、驗證或最終得分沒有提高」、「長鏈縮短來自過早停止，而非更高決策密度」。願意先寫下什麼會讓自己錯，在這類推廣性質的文件裡相當少見，也讓後續有人要複現時知道該量什麼。

**綜合判斷**：機制層面的描述（介面敏感性、狀態漂移、驗證覆蓋不足）值得參考，也與獨立第三方 repo 的觀察相互印證；benchmark 數字則應視為單次探索性結果，不宜當成選型依據。要用它做決策，該做的是拿自己的任務跑一次開關對照，而不是採信表格。

## 能不能架在目前這台機器上

這個問題的答案與報告內容無關，是純粹的容量計算。

### 手上的硬體（實測）

| 項目 | 值 |
|---|---|
| 機型 | `g6e.xlarge` |
| GPU | 1 × NVIDIA L40S，46,068 MiB（48.3 GB / 45.0 GiB） |
| vCPU / RAM | 4 / 30 GB |
| 磁碟可用 | 886 GB |
| 目前佔用 | 既有的 26B 服務佔 42.5 GB，剩約 2.9 GB |

### DeepSeek-V4 的權重需要多少

取自 HuggingFace API 回報的實際張量 dtype 分佈（查詢日 2026-08-18），而非參數量估算：

| | 參數量 | 權重位元組 | 需要幾張 L40S |
|---|---:|---:|---:|
| DeepSeek-V4-Flash | 290.9 B | **292.5 GB**（272.4 GiB） | **6.1 張** |
| DeepSeek-V4-Pro | 1,598.8 B | **1,601.9 GB**（1,491.9 GiB） | **33.2 張** |

兩個型號在 HF 上都已經是 FP8/INT8 量化過的權重（`quant_method: fp8`，主體張量為 I8），所以上面的數字已經是壓縮後的體積，沒有再靠量化省一輪的空間。而且這只算權重，還沒算 KV cache 與啟動值。

### 結論

**都不行，而且差的是數量級，不是調參能補的。**

- **V4-Flash** 需要整張卡的 6.1 倍。權重 292.5 GB 放得進 886 GB 的磁碟，但放不進 48.3 GB 的顯存。
- **V4-Pro** 需要整張卡的 33.2 倍。1.6 TB 連 886 GB 的磁碟都塞不下，得先擴磁碟才談得上下載。

CPU offload 也救不了：機器只有 30 GB RAM，連 Flash 的十分之一都放不下，而 MoE 模型逐 token 換入專家權重的頻寬需求會讓速度掉到不可用。

要自架的話，**V4-Flash 至少需要 7 張 L40S 才裝得下權重，實務上會用 8 張（約 386 GB）並開 `--tensor-parallel-size 8`**，剩約 90 GB 給 KV cache。V4-Pro 則已經超出單機範圍，要跨節點。

### 但 J-Space 不需要 GPU

這是關鍵的一點。J-Space Cognition Suite 是 15 個 markdown 檔加 3 支小 Python 腳本、總共 2.3 MB 的**提示詞協定套件**，不是模型也不是推論引擎。它在客戶端運作，疊在你呼叫的任何模型之上。

所以「能不能用 J-Space」與「能不能自架 DeepSeek-V4」是兩個獨立問題。**要試 J-Space，走 DeepSeek 官方 API 就行**，硬體完全不參與——這也正是報告自己的評測方式（用 DeepSeek Harness 打官方 API）。

本 repo 先前整理過 DeepSeek-V4 的 API 定價與 Claude Code 串接方式（換 `ANTHROPIC_BASE_URL` 到 `https://api.deepseek.com/anthropic`），見 [Subagent × 多模型分工](subagent-multi-model-cost.md)。

## 實務建議

1. **想用 J-Space 就直接走 API 試**，不需要動硬體。成本是 token 費用，不是 GPU。
2. **要驗證它有沒有效，做自己的開關對照**：同模型、同任務、同工具條件，只切換載不載入 J-Space，跑多次而不是一次，並同時記錄得分、耗時與 token 數。報告第 6 節列的證偽條件可以直接拿來當檢查項——特別是「得分上升是否只是換來更多 token 與時間」。
3. **不要拿報告的 benchmark 表當選型依據。** 跨廠商欄位不是同一 harness，同 harness 的部分是單次執行。
4. **那台 g6e.xlarge 的定位要認清**：45 GiB 顯存適合 30B 以下的模型，或是像目前這樣跑一個 26B 的量化模型。DeepSeek-V4 這個級距不在它的能力範圍內，差距不是「再省一點就能塞下」。
5. **報告裡真正可以立刻拿來用的是機制而非數字**：工具 schema 的寫法會改變模型軌跡、長任務需要顯式的狀態帳本、每個檢查訊號都該改變行動而不只是記錄。這三點不依賴 J-Space 也能套用在自己的 Agent 設計上。
