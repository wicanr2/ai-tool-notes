# 量化與 offload：速度算得出來，品質算不出來

「NVFP4 加上 offload 大概能跑多快」跟「不同量化下模型會笨多少」看起來是一組對稱的問題，實際上一個能從第一性原理推導到個位數精度，另一個沒有公式、只能量。

這篇把兩邊分開處理：先算 offload 的速度（並指出 vLLM 與 llama.cpp 的 offload 是兩種完全不同的機制，瓶頸不在同一個地方），再誠實面對品質那一題——說明為什麼它不可推導、能量什麼、以及其中**唯一一個真的算得出來的部分**：多步任務如何把每步的小損失指數放大。

- 相關：[推論速度怎麼估](llm-decode-throughput-formula.md)、[量化格式：FP8、NVFP4](quantization-fp8-nvfp4.md)
- 資料取自 vLLM 0.25.1 原始碼、ktransformers 官方教學與 HuggingFace 設定檔，查證日 **2026-08-18**
- 專案生態的完整整理見 [DRAM offload 專案地圖](dram-offload-projects.md)

## 一、offload 的速度：算得出來

### 兩種 offload，瓶頸不在同一個地方

「把權重放系統記憶體」有兩種實作路線，差別在**運算在哪裡發生**：

| 路線 | 權重放哪 | 運算在哪 | 每 token 的瓶頸 |
|---|---|---|---|
| **vLLM UVA**（`cpu_offload_gb`） | CPU pinned memory | **GPU** | 權重經 **PCIe** 送進 GPU |
| **vLLM prefetch**（`offload_group_size`） | CPU pinned memory | **GPU** | 同上，但非同步預取可與運算重疊 |
| **llama.cpp / ktransformers** | 一般系統記憶體 | **CPU** | **DRAM 頻寬**（權重不搬動） |

vLLM 0.25.1 的設定檔把 UVA 這條路講得很直白：

> 使用 UVA（Unified Virtual Addressing）零拷貝存取；**每一次 forward pass 都會把部分模型從 CPU 記憶體即時載入 GPU**，因此需要快速的 CPU-GPU 互連。

Prefetch 那條路則是把層分組、用非同步 H2D 預取把傳輸延遲藏在運算後面：

```
offload_group_size=8, offload_num_in_group=2  → offload 第 6,7,14,15,22,23... 層
```

還有一個對 MoE 特別有用的參數 `cpu_offload_params`，可以只針對特定參數名稱做 offload——填 `experts` 就只把專家搬到 host，attention 與 head 全部留在顯存。

**這個差別決定了公式的分母放哪個頻寬**：PCIe 5.0 x16 約 50 GB/s（實測），雙通道 DDR5 約 96 GB/s，八通道 DDR5 約 410 GB/s。

### NVFP4 這條路的限制

NVFP4 的運算需要 Blackwell 的 FP4 tensor core，CPU 沒有這個東西；而 llama.cpp / ktransformers 的生態是 GGUF 與 MXFP4，**不吃 NVFP4 格式**。所以 NVFP4 要 offload，只能是「權重放 host、運算留在 GPU」——vLLM 的 UVA 或 prefetch，瓶頸必然是 PCIe。

照這個路線估 `DeepSeek-V4-Flash-NVFP4` 在 RTX 5090 上（混合精度：只有 routed experts 是 4-bit，attention、shared experts、head 保留 FP8）：

| 組成 | 激活參數 | 精度 | 位元組 |
|---|---:|---|---:|
| routed experts（43 層 × top-6） | 6.49 B | NVFP4 0.5625 B/param | 3.65 GB |
| shared expert（43 層 × 1） | 1.08 B | FP8 1.0 | 1.08 GB |
| attention + head 等 | 5.43 B | FP8 1.0 | 5.43 GB |
| **每 token 合計** | **13 B** | 平均 0.78 B/param | **10.16 GB** |

全部 routed experts 是 155.8 GB 放不進 32 GB，只能放 host；必須常駐的 attention + shared + head 約 6.5 GB，扣掉 KV 與啟動值後約 22.5 GB 可快取熱門專家（均勻路由假設下命中 14.4%），於是每 token 有 3.13 GB 要跨 PCIe：

| PCIe 頻寬 | UVA（串接） | prefetch（重疊） |
|---|---:|---:|
| PCIe 5.0 x16，實測約 50 GB/s | 14.7 tok/s | 16.0 tok/s |
| PCIe 4.0 x16，實測約 28 GB/s | 8.5 tok/s | 9.0 tok/s |

這條路還有一個比速度更硬的門檻：UVA 要求 host 記憶體是 page-locked 的，**需要鎖住約 156 GB**。

### 實際被驗證過的是另一條路

上面是推導。實務上這個組合已經有人做出來並公開驗證了，而且用的不是 NVFP4：

[ktransformers](https://github.com/kvcache-ai/ktransformers) 的 KT-Kernel 搭配 SGLang，在**單張 RTX 5090** 上跑 `DeepSeek-V4-Flash-0731`，官方教學記載的解碼吞吐是 **20+ tok/s**。

| 項目 | 值 |
|---|---|
| GPU | 1 × RTX 5090（32 GB，SM_120）。RTX 4090 / 3090 也在驗證清單上 |
| 系統記憶體 | **≥ 200 GB** |
| 儲存 | 約 340 GB |
| 量化 | **MXFP4** routed experts，CPU 與 GPU 分攤 |
| 關鍵參數 | `--kt-num-gpu-experts 10`（256 個專家裡 10 個常駐 GPU）、`--kt-cpuinfer 60`（CPU 執行緒）、`--kt-enable-dynamic-expert-update` |
| context / 併發 | 16384 / 最多 2 個同時請求 |
| 啟動時間 | 4–5 分鐘 |

再加上 V4-Flash 內建的 NextN draft head 做 EAGLE 式推測解碼，還有約 1.2 倍（官方驗證數字：8×RTX 5090 上 26.5 → 32.74 tok/s，chain depth 1 下接受率 90%）。

**20+ tok/s 高於前面公式估的 14–16 tok/s**，差距的來源值得記下來，因為它揭示了公式裡最弱的假設：

1. **`--kt-enable-dynamic-expert-update`**：熱門專家會動態遷移到 GPU。公式假設路由均勻、命中率等於顯存佔比（14.4%），實際的專家使用有明顯熱點，動態調度後的有效命中率遠高於此。
2. **運算在 CPU 上就地做**，走的是 DRAM 頻寬而非 PCIe。`--kt-cpuinfer 60` 暗示這是一顆核心數很多的 CPU，記憶體通道數也遠多於桌機的雙通道。
3. **CPU 側用 INT4/INT8 量化權重**配合 AVX512/AMX，比純粹的頻寬模型更有效率。

換句話說，**公式給的是保守下界，實際實作靠熱點調度與 CPU 側最佳化把它往上推**。用公式做可行性判斷（「這個量級能不能跑」）很可靠；要預測某個特定實作的精確數字，就得看那個實作的調度策略。

### 三條路線的對照

| 路線 | 量化 | 運算在 | 瓶頸 | 速度 |
|---|---|---|---|---:|
| **ktransformers + SGLang**（實測） | MXFP4 | CPU + GPU 混合 | DRAM + 熱點調度 | **20+ tok/s** |
| vLLM UVA/prefetch + NVFP4（推估） | NVFP4 | GPU | PCIe 5.0 | 14–16 tok/s |
| llama.cpp + GGUF Q4，雙通道 DDR5（推估） | Q4_K | CPU | DRAM 96 GB/s | 13.6 tok/s |

所以對「單張 5090 能不能跑 DeepSeek-V4-Flash」這個問題，答案是**可以，約 20 tok/s，但你需要 200 GB 以上的系統記憶體與 340 GB 儲存**。記憶體容量而非顯卡，才是真正的門檻。

## 二、量化的品質：算不出來

### 為什麼沒有公式

速度那一題可以推導，是因為它的因果鏈很短：位元數決定位元組數，位元組數除以頻寬得到時間。每一步都是算術。

品質那一題的因果鏈是：量化誤差 → 權重擾動 → 中間表示偏移 → 逐層累積並被非線性放大 → 影響某個特定任務所需的某種能力。**最後一步不是數學問題，是經驗問題**：同樣大小的權重擾動，對「寫一段流暢的中文」幾乎沒有影響，對「一段 200 行程式碼的邊界條件」可能是致命的。

所以任何宣稱「4-bit 會讓模型掉 X%」的通用數字都應該被懷疑——那個 X 取決於模型、量化方案、以及你在測什麼。

### 能量的三種指標

| 指標 | 怎麼量 | 成本 | 資訊量 |
|---|---|---|---|
| **Perplexity delta** | 在一段語料上比較困惑度 | 低 | 弱。ppl 與下游能力的相關性不強，尤其在小差異區間 |
| **KL 散度 vs 原模型** | 同一批 prompt，比較量化前後的 next-token 機率分布 | 中 | **好**。直接量「它的思考偏離了多少」，不依賴任務選擇 |
| **Benchmark delta** | 跑實際任務 | 高 | 這才是答案，但要挑對任務 |

實務上的做法是**用 KL 散度篩選、用 benchmark 確認**：先用 KL 快速排除明顯壞掉的量化，再對候選跑真實任務。

一個常被忽略的細節：**評測必須用與部署相同的取樣設定**。temperature 0 下量化的影響會被 argmax 掩蓋掉一部分（機率分布變了但最大值沒變），而實際服務若用 temperature 1.0，那些被掩蓋的偏移就會顯現。

### 經驗上的曲線形狀

以下是文獻與社群實測上的**一般形狀**，不是任何特定模型的保證：

| 有效位元 | 典型影響 |
|---|---|
| 8 bit | 幾乎無損。多數任務差異落在量測雜訊內 |
| 6 bit | 近乎無損 |
| 5 bit | 小幅、視任務而定 |
| **4 bit** | **可測到。程式與數學先退化，日常對話幾乎看不出來** |
| 3 bit | 明顯。多步推理開始不穩 |
| 2 bit 以下 | 嚴重，除非用混合精度保護敏感層 |

### 五個會讓曲線左移的因素

**1. MoE 比 dense 更敏感。** 兩個原因：每個 token 只用到少數專家，誤差沒有被大量參數平均掉的機會；而且 router 的輸出要過 top-k，是**離散決策**——誤差不會讓結果「稍微差一點」，而是把 token 送去完全不同的專家。這也是為什麼實際的量化方案都把 router 排除在外（見 [量化格式](quantization-fp8-nvfp4.md)）。

**2. 模型越小越敏感。** 大模型的參數冗餘多，擾動有地方可以吸收。同樣 4-bit，在 7B 上的退化通常明顯大於在 200B 上的。

**3. 混合精度大幅改善曲線。** `UD-` 系列、`MIXED_PRECISION` 的 modelopt 版本，對 router、attention、head 保留較高位元。同樣標稱 4-bit，混合精度版本的實際表現可能接近 5–6 bit 的均勻量化。**比較量化版本時，位元數標籤本身沒有可比性。**

**4. 長 context 放大誤差。** 注意力要對整段 context 做加權，context 越長，被量化誤差影響的項越多。短對話測不出來的問題，在 32K context 下可能浮現。

**5. 任務型態有明確的敏感度排序。** 由不敏感到敏感大致是：閒聊 → 摘要 → 知識問答 → 多步推理 → 程式與數學 → **長程 Agent 任務**。

最後一項的敏感度遠高於其他，而它的原因是可以算的。

### 多步任務的放大效應：這一段算得出來

一個 Agent 任務要連續做對很多個決策才算成功。若每步的正確率是 `p`、共 `n` 步，且各步近似獨立：

```
端到端成功率 ≈ p ^ n
```

這個指數關係讓「每步掉一點點」變成「整體掉很多」：

| 單步正確率 | 1 步 | 5 步 | 10 步 | 20 步 | 50 步 | 100 步 |
|---|---:|---:|---:|---:|---:|---:|
| 100% | 100.0% | 100.0% | 100.0% | 100.0% | 100.0% | 100.0% |
| 99% | 99.0% | 95.1% | 90.4% | 81.8% | 60.5% | 36.6% |
| 98% | 98.0% | 90.4% | 81.7% | 66.8% | 36.4% | 13.3% |
| 95% | 95.0% | 77.4% | 59.9% | 35.8% | 7.7% | 0.6% |

換成「量化造成的相對損失」來看更直接。假設未量化時單步正確率 95%：

| 量化後單步掉幾個百分點 | 10 步任務的相對成功率 | 50 步任務的相對成功率 |
|---|---:|---:|
| 1 個百分點 | 90.0%（損失 10%） | 58.9%（**損失 41%**） |
| 2 個百分點 | 80.8%（損失 19%） | 34.5%（**損失 66%**） |
| 5 個百分點 | 58.2%（損失 42%） | 6.7%（**損失 93%**） |

**一個在單題評測上「只掉 1%、幾乎無損」的量化，在 50 步的 Agent 任務上會讓成功率掉四成。**

這解釋了兩件實務現象：為什麼量化模型在聊天時感覺沒差、一接進工具鏈就頻頻失敗；以及為什麼 Agent 場景的量化選擇應該比對話場景保守一到兩階。

（這個模型假設各步獨立且沒有錯誤恢復機制。實際系統若有 guard 攔截與 retry，衰減會比 `p^n` 平緩——但方向不變，只是斜率變小。反過來說，**投資在錯誤恢復機制上，等於買回被量化吃掉的成功率**。）

## 三、實務建議

1. **速度用算的，品質用量的。** 前者有公式且方向可靠（見[估算器](../tools/decode-throughput-calculator.html)），但要記得它給的是保守下界——真實實作的熱點調度會把數字往上推。後者沒有捷徑。
2. **要 offload，先算 host RAM 夠不夠，再談速度。** 官方驗證的配置要求 ≥200 GB 系統記憶體與 340 GB 儲存，這通常比速度更早卡住。
3. **單張 5090 跑 DeepSeek-V4-Flash 實測 20+ tok/s**（ktransformers + SGLang，MXFP4）。想要更快，加記憶體通道與開啟推測解碼比換顯卡有效。
4. **比較量化版本時不要只看位元數標籤。** 混合精度的 4-bit 可能勝過均勻的 5-bit，關鍵在哪些層被保護。
5. **Agent 場景的量化要比對話場景保守。** 用 `p^n` 估一下你的任務有幾步，再決定能接受多少單步損失。
6. **自己測的話，最小可行方案是**：取 30–50 題你真實場景的任務，量化前後各跑三次，比對完成率而非分數平均；同時記錄 KL 散度當快速篩選指標。這比引用任何通用的量化品質表都可靠。
