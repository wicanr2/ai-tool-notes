# 量化格式：FP8、NVFP4，以及模型怎麼搭配

同一個 DeepSeek-V4-Flash，官方 FP8 版本 292.5 GB，NVIDIA 的 NVFP4 版本 168.3 GB，社群的 GGUF `IQ2_M` 版本 90.9 GB。三份都是「同一個模型」，體積差 3.2 倍。

差別不只是位元數。把三份設定檔攤開看，會發現它們對「哪些層要量化」「多少個權重共用一個縮放係數」的決定完全不同——而那才是量化能不能維持品質的關鍵。

這篇拆解數值格式的取捨、縮放粒度為什麼比位元數更重要、哪些層碰不得，以及不同量化路線各自服務什麼場景。

- 相關：[推論速度怎麼估](llm-decode-throughput-formula.md)（量化省下的位元組如何換算成 tok/s）、[PEFT 與 LoRA adapter](peft-lora-adapter.md)
- 資料取自 HuggingFace 上的實際設定檔與檔案大小，查詢日 **2026-08-18**

## 一、量化在省什麼

量化把權重從高精度換成低精度，同時省下三種成本，但省的比例差很多：

| 成本 | 收益 | 重要性 |
|---|---|---|
| **顯存容量** | 線性下降。bf16 換 FP8 就是砍半 | 決定「跑不跑得起來」 |
| **記憶體頻寬** | 線性下降 | 決定「跑多快」 |
| **算力** | 只有硬體支援該格式的原生運算時才有 | 對 decode 影響小，對 prefill 有感 |

實務上**頻寬那一項最有價值**。自迴歸生成每產出一個 token 就要把權重讀一遍，所以生成速度直接與每個參數佔幾個位元組成反比——把 bf16 換成 FP8，單一使用者的 tok/s 差不多翻倍（推導見 [推論速度怎麼估](llm-decode-throughput-formula.md)）。

這也是為什麼「量化只是為了塞進小顯卡」是個誤解。在顯存綽綽有餘的機器上量化，仍然直接換到速度。

| 格式 | 每參數位元組 | 相對 bf16 的速度 |
|---|---:|---:|
| BF16 / FP16 | 2.0 | 1.0× |
| FP8 / INT8 | 1.0 | 2.0× |
| NVFP4（含 scale） | 約 0.56 | 3.6× |
| GGUF `Q4_K` | 約 0.53 | 3.8× |
| GGUF `IQ2_M` | 約 0.31 | 6.5× |

## 二、數值格式家族

### 浮點與整數的差別

同樣是 8 個位元，可以拿來表示 256 個等距的整數（INT8），也可以拆成指數與尾數表示不等距的浮點數（FP8）。差別在**動態範圍**：

- **整數格式**的表示點是等距的。要涵蓋大的數值範圍，最小的間隔就跟著變大，小數值的相對誤差會很大。
- **浮點格式**的表示點是對數分布的。接近零的地方密、遠離零的地方疏——這正好符合神經網路權重的分布（大量接近零的小值，少數大的離群值）。

位元數越少，這個差別越關鍵。到了 4 bit，浮點格式（FP4）幾乎必然優於整數格式（INT4），因為 16 個等距的點無法同時照顧離群值與主體分布。

### 格式對照

| 格式 | 位元配置 | 大致動態範圍 | 原生硬體支援 |
|---|---|---|---|
| FP32 | 1+8+23 | ±3.4e38 | 全部 |
| BF16 | 1+8+7 | ±3.4e38（與 FP32 同指數） | Ampere 以後 |
| FP16 | 1+5+10 | ±65504 | 全部 |
| **FP8 E4M3** | 1+4+3 | ±448 | **Ada / Hopper 以後** |
| FP8 E5M2 | 1+5+2 | ±57344 | Ada / Hopper 以後 |
| **FP4 E2M1** | 1+2+1 | ±6（只有 16 個值） | **Blackwell** |
| INT8 | 8 bit 整數 | ±127 | 全部 |
| INT4 | 4 bit 整數 | ±7 | 部分 |

兩種 FP8 的分工：**E4M3 尾數多一位、範圍小，用於權重與啟動值**；E5M2 範圍大、精度低，主要用於訓練時的梯度。推論場景幾乎都是 E4M3——本文後面三份實測設定全部是 `fmt: e4m3`。

FP4 只有 16 個可表示的值（`0, ±0.5, ±1, ±1.5, ±2, ±3, ±4, ±6`）。單獨看幾乎不可能用，它能運作完全靠下一節的縮放機制。

## 三、關鍵不是位元數，是縮放粒度

低精度格式的表示範圍很窄（FP4 只到 ±6），而實際權重的數值範圍遠超過它。解法是把權重除以一個**縮放係數（scale）**壓進可表示範圍，用的時候再乘回來：

```
量化：  q = round(w / s)          存 q（低精度）與 s（高精度）
還原：  w ≈ q × s
```

問題變成：**多少個權重共用一個 `s`？** 這就是縮放粒度，它決定了量化的品質上限。

| 粒度 | 一個 scale 涵蓋 | 品質 | 額外開銷 |
|---|---|---|---|
| per-tensor | 整個矩陣 | 最差（一個離群值毀掉整個矩陣的精度） | 可忽略 |
| per-channel | 一個輸出通道（一列或一行） | 好 | 很小 |
| per-block | 一個 128×128 的方塊 | 好 | 小 |
| per-group | 連續 16 或 32 個元素 | 最好 | 明顯 |

**位元數越少，粒度必須越細。** 直覺是這樣：FP8 有 448 的範圍，一整個通道共用一個 scale 也還撐得住；FP4 只有 6 的範圍，超過十幾個元素共用一個 scale 就會有元素被壓成 0。

### 三份實測設定的對照

| | `gemma-4-26B-A4B-it-FP8-Dynamic` | `DeepSeek-V4-Flash`（官方） | `DeepSeek-V4-Flash-NVFP4` |
|---|---|---|---|
| 權重位元 | 8（float） | 8（E4M3） | **4**（experts）/ 8（其餘） |
| 縮放粒度 | `strategy: channel` | `weight_block_size: [128,128]` | `group_size: 16` |
| 啟動值 | 8 bit，`strategy: token`，**動態** | 動態 | 4 bit，靜態 |
| scale 格式 | — | `scale_fmt: ue8m0` | E4M3 |
| 不量化的層 | `*.router.proj` | — | `*.attn.*`、`*.ffn.shared_experts.*`、`head`、`mtp.*` |
| 產出工具 | llm-compressor | 官方 | NVIDIA modelopt |
| 檔案體積 | — | 292.5 GB | 168.3 GB |

三種粒度剛好排成一個梯度：per-channel → per-block 128×128 → per-group 16。位元從 8 降到 4，粒度就從「一個通道」細到「16 個元素」。

### scale 的開銷讓 FP4 不等於 0.5 bytes

NVFP4 每 16 個權重配一個 FP8 的 scale：

```
每個權重的實際位元數 = 4 + 8/16 = 4.5 bit = 0.5625 bytes
```

MXFP4 用 32 個元素一組、scale 是 8-bit 指數（E8M0）：

```
4 + 8/32 = 4.25 bit = 0.53 bytes
```

所以估算速度時，「4 bit 就是 0.5 bytes」會低估 6% 到 12%。粒度越細，這個額外開銷越大——這是細粒度的代價。

## 四、只量化權重，還是連啟動值一起

| 標記 | 權重 | 啟動值 | 省頻寬 | 省算力 |
|---|---|---|---|---|
| W16A16 | bf16 | bf16 | — | — |
| **W8A16** | FP8 | bf16 | 是 | 否（要先還原成 bf16 再算） |
| **W8A8** | FP8 | FP8 | 是 | **是**（用 FP8 tensor core） |
| W4A16 | 4 bit | bf16 | 是（最多） | 否 |
| **W4A4** | FP4 | FP4 | 是（最多） | **是**（用 FP4 tensor core） |

AWQ、GPTQ、多數 GGUF 量化屬於 **weight-only（W4A16）**：權重壓小，運算前還原成高精度再算。這對 decode 很划算（decode 卡在讀取，算力有餘），但對 prefill 沒有幫助，還多了還原的開銷。

上面表格裡的 `gemma-4-26B-A4B-it-FP8-Dynamic` 是 **W8A8**：`input_activations` 的 `num_bits` 也是 8。名稱裡的 **Dynamic** 指啟動值的 scale 是**執行期依每個 token 即時算出**（`strategy: token`, `dynamic: true`），而不是離線校準的固定值。動態的好處是不需要校準資料集、對分布外輸入更穩；代價是每次前向都要多算一次 max。

NVFP4 那份走得更遠——`input_activations` 也是 `num_bits: 4`，是 **W4A4**。這只有在有 FP4 tensor core 的硬體上才有意義。

## 五、哪些層不能量化

兩份設定的 `ignore` 清單是最有資訊量的部分，因為它們揭示了模型裡哪些地方對數值誤差敏感。

**`gemma-4-26B-A4B-it-FP8-Dynamic` 排除的是 router**：

```
"ignore": ["model.language_model.layers.0.router.proj", ...]
```

MoE 的 router 決定每個 token 送給哪幾個專家。它的輸出經過 top-k 取樣，是**離散決策**——量化誤差不會讓結果「稍微差一點」，而是讓 token 被送去完全不同的專家。router 的參數量在整個模型裡微不足道，量化它省不到什麼，風險卻極高。

**NVFP4 那份排除的更多**：

```
"ignore": ["*.attn.*", "*.ffn.shared_experts.*", "head", "mtp.*"]
```

- `attn`：注意力的 Q/K 內積後要過 softmax，softmax 對輸入誤差是指數放大的
- `shared_experts`：每個 token 都會經過，誤差沒有被路由稀釋的機會
- `head`：直接產生 logits，誤差直接變成取樣機率的偏移
- `mtp`：multi-token prediction 模組

留下 4 bit 的只有 **routed experts**——它們佔了絕大多數參數，但每個 token 只用到其中六個，誤差有被平均掉的空間。

這就是 `quant_algo: MIXED_PRECISION` 的意思：**不是整個模型用同一種精度，而是按每一層對誤差的敏感度分配位元。** 這也解釋了為什麼 NVFP4 版本是 168.3 GB 而不是 4-bit 應有的約 164 GB——沒被量化的那些層仍然是 FP8。

一般性的原則：**參數量大、被稀釋的、線性的**可以壓；**參數量小、每個 token 必經、後面接非線性或離散決策的**不要碰。

## 六、硬體原生支援決定量化划不划算

| 世代 | 代表卡 | 原生支援 |
|---|---|---|
| Ampere | A100 | INT8、BF16 |
| Ada | L40S、RTX 4090 | **FP8**、INT8 |
| Hopper | H100、H200 | **FP8** |
| Blackwell | RTX 5090、B200 | **FP4**、FP8 |

沒有原生支援時，低位元格式仍然能用——但要在每次運算前把權重**還原（dequantize）**成硬體支援的格式。這件事本身要花時間，會讓 MBU 明顯下降，抵銷掉一部分頻寬收益。

實務推論：

- **L40S（Ada）跑 FP8 是甜蜜點**，有原生 tensor core。目前那台機器上跑的 `gemma-4-26B-A4B-it-FP8-Dynamic` 正是這個組合。
- **L40S 跑 NVFP4 不划算**——Ada 沒有 FP4 tensor core，只能靠 dequant，省了頻寬卻賠上算力與 MBU。
- **RTX 5090（Blackwell）跑 NVFP4 才發揮得出來**，W4A4 全程走 FP4 tensor core。

所以量化格式的選擇是**硬體綁定的**，不是「越小越好」。把 NVFP4 的模型搬到 Ada 卡上，得到的可能比 FP8 版本還慢。

## 七、三條量化路線的定位

| 路線 | 格式 | 生態 | 適合 |
|---|---|---|---|
| **compressed-tensors** | FP8、INT8、W4A16 | llm-compressor → vLLM | GPU 服務端，多使用者併發 |
| **modelopt** | NVFP4、FP8 | NVIDIA → TensorRT-LLM / vLLM | Blackwell 上的極致吞吐 |
| **GGUF** | K-quant、I-quant | llama.cpp、ollama、LM Studio | 單機、CPU offload、消費級硬體 |
| AWQ / GPTQ | W4A16 | 廣泛 | GPU 上的 4-bit weight-only |

GGUF 的量化命名是自成一格的體系。以 `unsloth/DeepSeek-V4-Flash-0731-GGUF` 的實際檔案大小為例（原始 FP8 版本為 292.5 GB）：

| 量化 | 體積 | 相對原版 |
|---|---:|---:|
| `UD-Q8_K_XL` | 161.9 GB | 55% |
| `UD-Q4_K_XL` | 155.1 GB | 53% |
| `UD-IQ4_XS` | 136.7 GB | 47% |
| `UD-Q3_K_XL` | 128.2 GB | 44% |
| `UD-IQ3_S` | 116.1 GB | 40% |
| `UD-Q2_K_XL` | 96.8 GB | 33% |
| `UD-IQ2_M` | 90.9 GB | 31% |
| `UD-IQ1_S` | 82.5 GB | 28% |

幾個讀法：`Q` 開頭是傳統 K-quant，`IQ` 開頭是 importance-aware 的 I-quant（用重要性矩陣決定哪些權重值得多花位元，同樣體積下品質較好，但推論時解碼較慢）。`UD-` 前綴是 Unsloth 的動態量化——**對敏感層自動保留較高位元**，跟前一節 NVFP4 的混合精度是同一個思路。

注意 `Q8_K_XL` 只比 `Q4_K_XL` 大 4%，因為原始模型本來就是 8-bit，`Q8` 幾乎沒有壓縮空間，而 `UD` 的動態策略又讓兩者的敏感層處理趨於一致。

品質的經驗排序：`Q4_K` 以上多數任務差異不明顯；`Q3` 開始在推理與程式任務上可測到退化；`IQ2` 以下退化明顯，`IQ1` 通常只用來證明「跑得動」。

## 八、量化與 LoRA adapter 的互動

這是實務上很容易踩的一個坑。

**LoRA adapter 的 `A`、`B` 是相對於特定精度的 base model 訓練出來的。** 在 bf16 base 上訓練的 adapter，套到 FP8 或 NVFP4 量化版上，就算張量形狀對得起來，行為也不保證——量化改變了 `W`，而 adapter 學的是「相對於原本那個 `W` 要調整多少」。

實務上的兩種情況要分清楚：

- **QLoRA** 是**訓練時**把 base 量化成 4-bit 以節省訓練顯存，但 LoRA 分支仍以高精度訓練。產出的 adapter 對應的仍然是原始的高精度模型，部署時不需要也不應該綁定同一個量化版本。
- **部署時量化 base 再掛 adapter**，是把 adapter 套到一個它沒見過的權重上。可以跑，但評測數字必須重新量。

保守做法：**adapter 用哪個精度的 base 訓練，就用哪個精度部署**。要換精度就重新評測，不要假設分數會轉移。細節見 [PEFT 與 LoRA adapter](peft-lora-adapter.md)。

## 九、怎麼選

1. **先看硬體世代**。Ada / Hopper 選 FP8，Blackwell 才考慮 NVFP4，Ampere 以前用 INT8 或 W4A16。硬體沒有原生支援的格式，省下的頻寬會賠在 dequant 上。
2. **顯存夠就別過度量化**。FP8 在多數任務上與 bf16 幾乎沒有可測差異，再往下每一階都要付品質代價。
3. **要壓到 4 bit 以下，找混合精度的版本**。`UD-` 系列、`MIXED_PRECISION` 的 modelopt 版本，都會對 router、attention、head 保留較高位元。純均勻的低位元量化在 MoE 上退化特別嚴重。
4. **GPU 服務用 compressed-tensors 或 modelopt，單機 offload 用 GGUF**。這兩條路線的工具鏈與最佳化方向不同，混用會兩邊都不順。
5. **換量化格式一律重新評測**。體積與速度可以用算的（見 [推論速度怎麼估](llm-decode-throughput-formula.md)），品質不行。
