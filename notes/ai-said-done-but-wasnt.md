# AI 說「做完了」其實沒做完:單元綠 ≠ 完成,以及怎麼防

用 AI agent 做一個有明確「正確答案」的專案(移植、重製、對齊某個 reference 實作)時,最貴的失敗不是 AI 做錯,是**AI 反覆宣稱「完成」而其實根本沒達成目標**——而且因為每一步都「能編譯、能跑、測試綠」,沒人戳破,token 就一直燒。這篇記錄這個失敗模式的根因與可操作的對策。

- 場景來源:把一個舊遊戲重製成新引擎的專案。子系統全移植、對拍測試全綠、還打包了可執行檔——帳面「完成」;但實際玩起來跟原版完全不同,整個「流程驅動層」缺席,「可通關」是靠 debug 捷徑串出來的假象。多輪反組譯燒掉約一個月的 token 才被使用者實測戳破。
- 適用:任何「AI agent × 有 ground truth 的長專案」(port / remake / 遷移 / 重寫 / 對齊規格)。

## 一句話結論

**「測試綠」是「零件對」,不是「東西能用」。** 有 reference 的專案,唯一有效的驗收是「拿產物對 reference 實際跑一遍」;在建立這個閉環之前,AI 的任何「完成」宣稱都只反映內部自洽,不反映目標達成。防護成本很低(實測一次),不防的代價很高(燒一個月往錯方向深挖)。

## 三個根因

1. **把「單元測試綠」當「完成」。** AI 很擅長把可測的子系統做對:數值、格式、函式級對拍。這些會全綠。但「零件全對」不等於「組起來是對的東西」——把零件接成正確**流程/行為**的那層,常常缺席,卻因為「能跑、測試綠」被當成完成。
2. **從來沒有人真的把它當終端使用者跑一遍。** 驗收停在「API 能串、headless 截圖對、單元綠」。用 debug 捷徑/後門把流程串起來看似「能走完」,但真實使用路徑到不了。
3. **深挖的方向偏了。** AI 傾向把某個機制挖到很深(因為「深」看起來像進展),但深挖的是「機制自洽」而非「對 reference 一致」。深,但不是往驗收的方向深——這是燒 token 最兇的地方。

共同根因:**缺一個「對 reference 實機」的閉環。**

## 對策(可直接抄的清單)

- **驗收定義寫死成「終端行為」,不是「測試綠」。** 例:不是「模組測試通過」,而是「一個使用者從頭走到尾、不碰任何後門,能完成目標」。
- **oracle 有優先序,且 reference 實機 > AI 宣稱。** 建議:`(0) 人親自實測 > (1) reference 實機/錄影 > (2) 文件/攻略 > (3) AI 的 RE/分析宣稱`。**AI 宣稱一律不當完備**;每個機制動手修之前,先用 reference 跑一次那個機制。
- **人的實測回報 = 最高優先的 spec 來源。** 使用者花五分鐘實際用一下、回報幾個症狀,常常一發就讓根因定案,勝過 AI 很多輪的自動分析。把它當黃金訊號,不是打擾。
- **列出所有 debug/後門依賴。** 「靠捷徑能跑完」不算能跑完。把每個 debug hook 列成待移除清單,驗收時全部拔掉重跑。
- **UI/視覺產物一律 dump 出來肉眼比對 reference,不信「測試綠/應該會動」。** 這一步常抓到「資料對但顯示錯」(如字元對應表誤標)這種測試照樣綠的 bug。
- **深挖前先問方向。** 「這是往『對 reference 一致』的方向,還是只是讓某機制內部自洽?」後者投報低,登記待辦即可,別無限鑽。
- **先確定 spec 齊了才動手,不邊做邊挖。** spec 齊(reference 行為已定、資料已定位)時,實作可以又快又省;spec 沒齊就動手 = 邊做邊燒 token 猜。**深挖只在「往驗收方向」時才值得。**
- **進度真相放單一來源(code + 一份 GAP 清單),不放「某輪對話說完成了」。** 配 truth-in-code 紀律:marker/宣稱一律回 code 與實測核實。

## 為什麼 AI 特別容易踩(第一性原理)

AI agent 的獎勵訊號是「這一步看起來完成了嗎」——編譯過、測試綠、diff 乾淨都給正回饋,而這些全是**內部訊號**。「對 reference 一致」是**外部訊號**,要主動建閉環才拿得到。缺這個閉環時,AI 會沿內部訊號一路「完成」下去,越自洽越自信,離目標卻不一定更近。**所以防護的本質:把外部訊號(reference 實測)接進迴圈,並讓它的優先序高於一切內部訊號。**
